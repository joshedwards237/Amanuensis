Shipped PRs #27–#34: the level-path guard, the nil-screen non-fault, the sweep counter that reported recordings as transcripts, session-error routing, PRD §11.5/§11.6, and this fix.
- **Surprise**: **The daemon told the user "Amanuensis — something failed; see the terminal" and nothing had been told to the terminal.** `session.error` held the exception the whole time and *no surface carried `session.error`* — `tray.set_error` was wired to the overlay's failures and the hotkey switcher and to nothing in the dictation path. So I bisected: engine, VAD, guard, post-processing, persistence, injector permissions, and the overlay against real AppKit, all clean in isolation, **because the failing stage never named itself**. Then he restarted and the evidence was gone permanently. The root cause is still unknown and I said so rather than constructing a plausible story from the symptoms — which was tempting, because by then I had four candidate mechanisms that each explained part of it. What I could offer instead was a latent wedge found while looking: `end_session` cleared `_recording` only *after* `capture.stop()`, and `start_session` returns early while that field is set, so one raise from a detaching headset made every later press a silent no-op — no capture, no overlay, no row, until a restart. It matches the report exactly and is not provably its cause, and the fix is committed as the former rather than the latter. Second surprise, smaller and worse: **the stress pass over S1 found that the level path was still unguarded** — `set_level` dispatched `_draw_bars` raw, on the path that runs thirty times a second, where an exception terminates the process. S1's entire subject was "the overlay dies without saying so" and I had extended the guard to the state path and never asked about the other one.
- **Proposal**: For GOTCHAS, two. (1) **When a running system reports that something failed without reporting what, fix the reporting before diagnosing.** One line of output ends the search; an hour of elimination does not, and the next restart erases the subject. The tell is the sentence itself — any message of the form "something went wrong, look elsewhere" is a claim that the product knows and is not saying, and the cheap move is to find where it knows and route it out. Then ask where the message survives a restart: a menu row and a terminal window both die with the process, which is what made this unrecoverable rather than merely slow. (2) **In teardown, clear the state before the fallible call, not after.** The damage is never the unclosed resource; it is the next early-return guard reading a field that no longer means what it says, turning every subsequent attempt into a silent no-op. And testing it needs the resource, not the state: asserting the controller ends in RECORDING passes against the bug, because the wedged session left it there — three of my tests today could not fail until sabotage said so, and the discriminating assertion was always a counter on the fake rather than a flag on the object.
- **Improvement**: **The reporting surface is the last thing anyone tests and the first thing needed when something breaks.** This session added a fault mark to the menu-bar title (finding 3) and then, on the same day, discovered that the *dictation* path had no route to any surface at all — two halves of one hole, found a day apart, the second only because a live failure walked into it. The generalisation: every state a product can enter needs a named way for a human to learn *why* it entered it, and "the state is visible" is not that. §5.4 has carried this argument since before the overlay existed and it was applied to the microphone indicator and nowhere else. Separately, and this one is about me: I wrote **five** successive versions of one test in S1 that could not fail — sticky fake state, failure injection at a call the code reaches only once, arithmetic that let a success land inside every burst — and found every one by sabotage rather than by reading. Sabotage is no longer a final check in this project; it is the only thing that has ever caught this class, and the honest conclusion is that I cannot see a hollow assertion by looking at it.
- **Gotcha found in the method, not the product**: **the sabotage loop can lie, and it lied today.** Copying a source file out, editing it, running the suite and copying it back happens well inside one second, and CPython's bytecode cache invalidates on a second-resolution mtime — so a restored file kept running its sabotaged bytecode and reported a failure that did not exist. I read the source, confirmed it was correct, and watched the test fail against it three times before suspecting the cache. Any sabotage pass in this repository should `find . -name __pycache__ -type d -exec rm -rf {} +` between the restore and the re-run, and a sabotage result that contradicts the source is a cache result until proven otherwise.
- **Constraint**: Proposed for HARNESS.md — **every code path that sets a user-visible error state must route its message to a surface, and a test must assert the message arrives.** Falsifiable mechanically: grep for `_set_state(DictationState.ERROR)` and require an adjacent report call; more usefully, a test per path that asserts the callback received the text and a control that a success clears it. This close would have turned a morning into a minute. Second, and narrower: **a teardown that clears state after a fallible call is a defect shape worth grepping for** — `self._x = None` following a call that can raise, where something guards on `self._x`.
