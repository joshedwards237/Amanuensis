- **Date**: 2026-09-14
- **Agent**: main session (lane 6's first install — README restructure, three permission fixes, a diagnostic)
- **Task**: Restructured the README around the install path, then fixed the defect lane 6's first unaided installer hit: the product told him to toggle a row in System Settings it had guaranteed would not be there. Three fixes, PRs #40–#44.
- **Surprise**: **Two of the three fixes did not work, and every check I had said they did.** `CGRequestPostEventAccess` shipped with 707 green tests, `mypy --strict` clean, and a sabotage run confirming the new tests went red without it — and it registered nothing on the reporter's macOS 26.6. Its replacement shipped the same way and had *half* of it measured broken on the same machine hours later. The reason is structural: both development surfaces run **27.0 with both grants already held**, so the failing state is unreachable here by construction, and **every check passed for the same reason the bug was invisible**. The rehearsal I was proudest of — a fresh local user account created specifically to walk this lane — could not see it either, because it was a fresh account on the same OS; it controlled the variable that was fine and not the one that mattered. Second surprise, and the one with teeth: **the fix for the fix nearly shipped inverted.** `manu --version` was meant to answer "am I running the code I pulled", and the obvious implementation — `git -C <package dir> rev-parse HEAD` — reports a *copied* install as editable whenever the venv sits inside the checkout, which is exactly where the README puts it and exactly where the reporter's is. The naive version would have been wrong for the only person whose install prompted the work, and my first probe passed because I built it in a scratch directory outside any repo. Third: an assertion I had written the day before, `assert not hasattr(quartz, "CGRequestListenEventAccess")`, was a fact about the test double that no product behaviour could falsify.
- **Proposal**: For GOTCHAS, one, and it is about *sequencing* rather than rigour. **When the falsifying environment belongs to another person, stop fixing and build an instrument.** Two failed remote fixes is the signal, not three. Each blind fix cost him a pull, a reinstall, a trip through System Settings and a report — four steps to test one hypothesis — and produced a single bit. `scripts/diagnose_permissions.py` cost one message, ran every candidate API in one pass, and returned a table that settled three open questions at once including one I had not thought to ask. The economics are not close and they are visible *before* the first blind fix, not after the second.
- **Improvement**: **Ask for the artefact's identity before diagnosing anything about its behaviour.** A full round trip was spent on "the fix didn't work" that was unanswerable because nobody had established which code was running — `pip install .` is not editable, so his `git pull` updated the checkout and left the installed command untouched. `manu --version` now prints the version, the directory the code is in, and whether git *tracks* that directory; that should have been the first question of the sequence rather than the third fix in it. Related: when a second person is the only instrument, **batch every question into one artefact they run once.** I asked him to look in a Settings pane three separate times, and the third time he was looking in the wrong pane because I had fixed one grant and not the other.
- **Constraint**: Proposed and added to HARNESS.md — **a fix is unverified until it runs where it can fail.** A fix for a defect observed on a configuration this machine does not have is not verified by a green suite here; say so in the PR and the gate record, and name the configuration that would falsify it. Enforcement is honestly `none` and there is no mechanical version, because the missing configuration is by definition absent from the machine running the check — the enforcement is the disclosure. Corollary recorded in `docs/gates/phase-4.md` finding 4a: the operator cannot verify lane 6 defects on the operator's machine, so a second OS version is not optional equipment for that gate.
