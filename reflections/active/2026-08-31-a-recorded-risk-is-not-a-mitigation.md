- **Date**: 2026-08-31
- **Agent**: main session (the landing page — spec, data pipeline, page, three-route redesign)
- **Task**: Built and deployed a landing page for the project at `site/`, published to GitHub Pages. Three design directions generated independently and synthesised into `docs/site/SITE_PRD.md`; two sentinels (advocatus-diaboli, choice-cartographer) reviewed it across four spec revisions; then the export pipeline, the replay widget, the page, CI and the deploy. Merged as PR #10, then restructured into `/`, `/how-it-works` and `/docs` with new type and colour as PR #11 after the first version read as a technical document rather than a product page.
- **Surprise**: **The failure that shipped had been written down, by name, before implementation started — and writing it down felt like handling it.** The choice cartographer's report said the single-route structure staked the audience bet whole: no shallow surface for the skimmer, no deep one for the checker, and it named that the page's best material sat thousands of words below the fold. I read that, agreed with it, and promoted it into the spec as §13.1 "the page is optimised for the reader who checks, and most visitors do not" — with a mitigation paragraph explaining that the hero was self-sufficient. Then I built it, deployed it, and the operator's first reaction was that it was very wordy and did not read as a product page. That is not a new finding; it is §13.1 arriving on schedule. **A risk recorded with a mitigation reads like a risk that was handled, and the difference between "we considered this" and "we changed something because of it" is invisible in the document.** The cartographer had also flagged that the one-route decision was the only item on the spec's cut list with *no reason attached* — a decision recorded as a prohibition rather than a trade — and I left it that way through two more revisions. The second surprise is smaller and worse: while writing the README correction *for this very close*, I published `n = 4` for the 16–60 s latency band. Four is the synthetic test fixture's count. The real database has seven. I was three sentences into a paragraph withdrawing someone else's unreproducible number when I copied one from the wrong source, and only caught it because I re-ran the derivation before committing.
- **Proposal**: For GOTCHAS, two. (1) **A spec risk that has a mitigation paragraph and no changed decision should be labelled as accepted, not mitigated.** §13.1 described the hazard accurately and changed nothing about the design; the redesign cost a full rebuild of the page's structure, type and copy. The cheap version of that decision was one question — "is this a product page or a technical document?" — asked before the spec rather than discovered after the deploy. Where a sentinel names a structural risk, the disposition should say explicitly which of *changed the design*, *accepted with a named trigger to revisit*, or *rejected the objection* applies, because "wrote a paragraph about it" currently reads as all three. (2) **Numbers copied from a test fixture are the same defect as numbers copied from prose, and the fixture is the more convincing source.** This repo already records "re-derive any number before quoting it" and it did not save me, because a fixture *feels* like a measurement — it is machine-generated, it lives in the repo, it came out of the real schema. The discriminating question is not "is this number real" but "is it from the database this sentence is about". Three separate wrong figures this sprint had the same shape: `p95 270.0` copied from a README, `transcribe_ms ≈ 49 + 13.7 × seconds` copied from `CLAUDE.md`, and `n = 4` copied from `history-fixture.db`.
- **Improvement**: **Check the tree is current before reading it, and treat a stale read as poisoning everything downstream of it.** Revision 1 of the site spec was written against a lobby checkout one commit behind `origin/main`, in which Phase 3 appeared unbuilt. It specified a widget track labelled "not built — Phase 3" for a stage that had shipped three weeks earlier, and a whole section on what the product could not yet do. That was not a small correction: both sentinels then reviewed the stale spec, so one of the twelve adversarial objections (O2, "Phase 3 will invalidate every artefact here") was moot on arrival, and the choice cartographer reasoned about a postprocess track that should never have existed. One `git fetch` before the first read would have prevented a spec revision, part of a review round, and the rework of both. The session-start hook *did* report the branch as stale and I read past it. Related, same shape at a smaller scale: `mypy --strict` passed locally because I had worked around a missing `py.typed` with `MYPYPATH=src` on the command line, then wrote the CI step without it — so the check that was green on my machine was a different check from the one CI ran, and CI failed on the first push.
- **Constraint**: Proposed for HARNESS.md — **a document that quotes a measurement must name the source that produced it, and that source must be the one the surrounding claim is about.** Falsifiable by sampling: for any figure in a spec, README or gate record, the text names its origin (`history.db`, a named gate record, a named experiment, a fixture) and re-running that origin reproduces the figure. This sprint produced the mechanism for the site half of it — `scripts/verify_site_claims.py` regenerates every published number from a committed fixture and diffs it, with a negative control that must produce a diff and a positive that must not — and the same discipline is what the prose documents lack. Verified by sabotage: blinding the export to `transcribe_ms` fails the negative control while the positive control still passes, which is why one control is not enough.
