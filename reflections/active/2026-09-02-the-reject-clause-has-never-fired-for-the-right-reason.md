- **Surprise**: **The gate returned REJECT, so I audited the classifier. Had it returned PASS I would not have looked.** The classifier really was wrong — it bucketed edits by the *shape* of a difference where §9's clause is about *responsibility*, and on the same corrections file the surface split called 107 of 171 edits chain-attributable while the responsibility split calls it 8. The rewrite survives sabotage in both directions. But the trigger for examining it was a verdict I disliked, which is objection O4's shape running backwards: O4 was about a gate that could not fail, and this is an auditor who audits only failures. I named it in the report at the time and then *still* did not run the discriminating test until the retrospective — scoring the previous corpus through the fixed classifier. Run now: August reads 7.67% with chain 3 against decoder 195, and passes under both classifiers. **Neither corpus discriminates**, so the fix rests entirely on its own controls, and the audit I eventually ran was too weak to be the vindication I would have claimed for it. Second surprise, and the one with teeth: **the reject clause has still never fired for the right reason.** It has fired exactly once in this project's history, on a misattribution, and that firing was then removed by fixing the misattribution. A gate whose failing state has been observed only as an instrument bug is a gate whose failing state has not been observed.
- **Proposal**: For GOTCHAS, two. (1) **Audit the instrument when it agrees with you, not only when it does not.** The tell is procedural rather than technical: if the reason you opened the classifier was the verdict, the audit is downstream of the outcome and cannot clear it. The cheap fix is that any instrument change which flips a verdict must be re-run against every prior corpus *and the result stated*, including when — as here — the prior corpus cannot tell the two instruments apart. "It passed both ways" is a finding about the corpus's discriminating power and belongs in the record next to the fix. (2) **Recall is not precision, and a rule is priced in the direction it runs.** I measured that **70%** of the sentence marks the operator added sat on a Whisper segment boundary, and nearly sized a rule on it. The rule runs on boundaries, of which there are 95 across ten takes, and only **31%** want a mark. Measured end to end it produced 29 correct insertions against 66 invented and moved edit rate 9.59% → 12.35%. The question a rule answers is "of the places I will fire, how many should I" — never "of the places I should have fired, how many did I reach".
- **Improvement**: **Record the configuration that produced a measurement at the moment of measuring.** `history.db` stores nine latency columns, guard coverage, retained seconds, raw and post-processed transcript — and nothing about the config that produced any of it. The consequence was two weeks of a corpus nobody knew was invalid, a gate scored against a dead configuration, and the operator re-recording twenty minutes of dictation and rewriting ten transcripts of corrections. It was found only because an unrelated investigation into one take's missing 21.7 seconds reached `config.toml`'s mtime and compared it to the last `started_at`. Nothing about that discovery was systematic. Separately and worth keeping: the ordering that *did* work was refusing to write the gate record until the corpus was re-recorded — the temptation was to publish 8.63% with a caveat paragraph, and this project already knows that a risk recorded with a mitigation paragraph reads as a risk handled.
- **Constraint**: Proposed for HARNESS.md — **every stored measurement row carries a digest of the configuration that produced it, and a gate refuses a set whose rows disagree.** Falsifiable mechanically: `history.db` rows carry a `config_sha256`, `gate_phase3.py` rejects when the gate's ten rows do not share one, and a row written after a config edit produces a different digest. This close would have caught the dead-config corpus on the first gate run rather than the third, and the check costs one column and one comparison. Second, smaller: **a gate's reject path needs a control of its own.** `classify_edits` has nine controls and the reject clause has none — the gate has never been observed refusing a set for the reason it exists to refuse.
