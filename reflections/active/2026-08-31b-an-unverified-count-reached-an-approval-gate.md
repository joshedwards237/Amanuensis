A reflection fragment for the sprint was written earlier in the same close; this one covers only what happened after it.
- **Surprise**: **I put a wrong count in front of the operator as the basis for an approval, and the wrong count was produced the same way as the two I had just finished correcting.** Presenting the cleanup list, I wrote "remote branches for merged PRs #1, #3, #4, #5, #8, #9, #10 — seven branches on origin" and asked for approval to delete them. Five existed; `phase-0-scaffolding` and `phase-3-postprocessing` had already been deleted from origin. I had counted *merged PR numbers* and inferred branch existence from them rather than running `git ls-remote --heads`, which takes a second and is the only thing that answers the question actually being asked. The operator approved "delete all seven". **The number did not merely get published — it was the thing a human authorised against**, which is a worse failure mode than the two earlier ones and I did not notice the difference at the time. Third instance in one session of the same shape: `p95 270.0` copied from a README, `n = 4` copied from a test fixture, and now a branch count inferred from a PR list. What makes this one different is the timing: I had written a memory file about exactly this defect roughly fifteen minutes earlier, during phase 4 of the same close.
- **Proposal**: For GOTCHAS — **a number that gates someone else's decision must be derived at the moment it is presented, not inferred from an adjacent list.** The tell is grammatical: "branches for merged PRs" is a claim about PRs wearing the costume of a claim about branches, and the two are only equal if nothing has deleted a branch since. Every count offered for approval should have a command next to it that produced it; if there is no such command in the transcript, the number is a guess. Cheap and mechanical: `git ls-remote --heads origin` before proposing remote deletions, `git worktree list` before proposing worktree removals, and quote the output rather than a summary of it.
- **Improvement**: **Writing a lesson into memory is not the same as having learned it, and the gap can be measured in minutes.** Phase 4 of this close promoted `a-quoted-number-is-unverified-until-it-reproduces` with a new section specifically about numbers copied from convincing-but-wrong sources. Phase 6 then produced another one. That is the same shape as the sprint's headline finding — a risk recorded with a mitigation paragraph reads as a risk handled — applied to memory rather than to a spec: *the act of writing it down discharges the feeling of owing something to it*. The practical fix is not another memory file. It is that the promotion step should end by naming the **next place in the current session** where the lesson would apply, and checking that place before moving on; a lesson promoted at 16:40 had an obvious application at 16:52 and nothing connected them. Separately and more positively: presenting destructive cleanup as a **classified** list — safe, will-refuse, keeping-regardless — and letting `git branch -d` refuse on the squash-merged branches rather than routing around it with `-D` was confirmed by the operator as the right shape. Squash-merged branches always read as unmerged to git, so that refusal is a permanent feature of this repo's history and not a problem to solve.
- **Constraint**: Proposed for HARNESS.md — **any quantity presented to a human for approval carries the command that produced it.** Falsifiable by inspection of the transcript: for every count, list length or figure in an approval request, a command in the immediately preceding turns produced that exact number. This close would have failed the check twice — the seven-branch count, and the `n = 4` band size in the README correction — and both were caught only by re-deriving after the fact.
